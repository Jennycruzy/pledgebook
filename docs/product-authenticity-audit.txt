PLEDGEBOOK DEEP PRODUCT AND PRODUCTION-READINESS AUDIT
Date: 2026-09-29
Revision reviewed: c18b2e6
Deployment: https://pledgebook.54-154-121-30.sslip.io/

VERDICT

The redesign is a substantial rebuild. Authentication, organisations, roles,
event lifecycle, guest pages, settlement, activity, sample isolation, and the
revised microphone workflow now exist. All 101 repository tests pass locally,
and the committed report records 21/21 rejected break-in attempts.

It remains a controlled pilot, not a production-ready financial product. Two
important authorization/ledger defects are absent from the current tests, live
payments and email are not enabled, and the speech-quality claims do not yet
have a benchmark.

HIGH-PRIORITY DEFECTS

1. Event-specific usher invitations grant organisation-wide event access

The invite stores event_id and the UI promises that the usher sees "only this
queue and the register." On acceptance, however, the code creates a membership
containing only org_id, user_id and role. require_event then authorizes every
event in that organisation from that organisation-wide membership. The event_id
is not enforced after acceptance.

Impact: an usher invited to Event A can open Event B in the same organisation,
including its register and review queue. Contact/export permissions remain
restricted, but the event confidentiality boundary is broken.

Evidence: app/auth.py lines 180-199 and 225-240; app/db.py lines 23-35;
web/app.js line 639.

Required fix: introduce event-scoped staff grants, enforce them in every event
API/WebSocket/audio path, and add a two-event regression test.

2. Offline payments can exceed the outstanding pledge

The offline-payment endpoint accepts any positive amount and credits it without
comparing it with the pledge balance. The Paystack path has overpayment
protection, but cash/transfer/cheque/POS entry does not.

Impact: a staff mistake can make received totals exceed pledged totals and
corrupt settlement reporting.

Evidence: app/followup.py lines 162-188.

Required fix: reject amounts above the balance, or use a separate audited
adjustment workflow, and test exact, partial, repeated and excessive entries.

3. Owners can permanently delete payment and audit history

An owner may delete any non-live event even after money has been received. The
deletion hard-removes payments, calls, audit records, pledges, guests and audio.

Impact: financial evidence and the activity trail can be destroyed.

Evidence: app/main.py lines 481-493; app/core.py lines 235-241.

Required fix: archive settled events, make financial/audit rows append-only,
and define exceptional deletion and retention rules.

PRODUCTION BLOCKERS AND UNPROVEN PATHS

4. Payments remain in Paystack test mode. No completed public test-card payment
plus signed webhook round trip is recorded; unit tests use a stand-in.

5. Email is not configured live. WhatsApp/SMS actions prepare links on the staff
device; they are not managed outbound delivery.

6. No benchmark has been run. The repository explicitly says there are no
public accuracy, wrong-person, latency, time-saving, fulfilment or cost numbers.
Current evidence is one 70.4-second recording from one speaker. The landing
claim that each pledge appears "in about two seconds" is stronger than this.

7. A complete guest Voice Agent conversation in a real browser is not recorded
as a reproducible acceptance test. Recognition of a corrected name on its next
real spoken mention also remains to be demonstrated.

8. The claimed desktop/mobile/light/dark browser sweep has no committed,
repeatable browser suite, screenshots or console artifact. CI's browser check
only syntax-checks web/app.js and web/pay.js. The manual claim may be true, but
another engineer cannot reproduce it from the repository.

SECURITY AND ACCOUNT GAPS

9. The live HTTPS response does not send Strict-Transport-Security. CSP exists,
but permits unsafe-inline styles. Add HSTS after confirming HTTPS-only service.

10. Email ownership is not verified. There is no forgot-password/reset, MFA or
account-deletion flow. An email-restricted invite checks a typed account email,
not proven control of that inbox.

11. Rate limiting is in-process and resets on restart. This supports only the
documented single-server pilot.

12. Private pledge-page bearer tokens are random and expiring, but stored in
plaintext in SQLite. Store token hashes so a database read does not expose all
active private links.

OPERATIONS AND SCALE

13. SQLite and in-process event delivery bind the service to one app instance.
Multi-instance operation needs a shared database and message bus.

14. There is no automated backup/restore drill, monitoring, alerting or error
reporting evidence. /healthz is useful but insufficient by itself.

15. Schema evolution uses runtime additive column checks rather than versioned
migrations. This becomes risky as production data and rollback needs grow.

16. Online payment is NGN-only. Other currencies are offline-only.

WHY PARTS STILL LOOK LIKE A MOCK

17. The landing hero is scripted with fixed fictional names, amounts, a starting
total and a private-page payment state. It is marked as an illustration only for
accessibility, while visually resembling live data. Add a visible "Illustrative
preview" label and avoid realistic paid-state copy unless it opens a sandbox.

18. The repository still uses judge/evaluation language and the defensive phrase
"real product, not a demo." This feels like a submission. Move evaluation
material away from the primary product docs and emphasize operator setup,
deployment, security, recovery and support.

19. Documentation says the sample has three invented guests, but code seeds
nine. Evidence: docs/judge-guide.md lines 10-12 and app/sample.py lines 19-29.

20. README and historical verification material still mention Chief Emeka
Okonkwo. He is not in runtime sample data now, but the prominent recurring name
preserves the canned-demo impression.

VERIFIED STRENGTHS

- Revision c18b2e6 is deployed and committed as jennycruzy.
- Full local suite: 101 passed, with one dependency deprecation warning.
- Authentication, tenant ownership, hashed sessions and role permissions exist.
- Event lifecycle, My Events, guest administration and activity UI exist.
- Voice tokens and event data are no longer anonymously exposed.
- Signed Paystack webhook validation and online overpayment/idempotency checks
  exist in code and tests.
- Sample events are visibly labelled and expire after 24 hours.
- The 21-case report covers anonymous, cross-organisation, CSRF, role, token,
  assistant-tool and payment attacks.

TEST/REPOSITORY HYGIENE

21. pytest is not declared in requirements.txt; CI installs it separately. Add
a development requirements file or test extra for reproducibility.

22. The suite emits a Starlette TestClient warning that the httpx transport is
deprecated and recommends httpx2. Track this before dependency updates turn it
into a failure.

RECOMMENDED ORDER

1. Fix event-scoped usher authorization and add cross-event tests.
2. Prevent offline overpayment and make settled financial history immutable.
3. Run a public Paystack test-mode webhook round trip and preserve evidence.
4. Add repeatable browser E2E tests for microphone permission/capture, mobile,
   both themes, guest voice and payment return.
5. Record the prepared multi-speaker benchmark before publishing performance.
6. Configure email, backups, restore drills, monitoring and password recovery.
7. Clearly label scripted previews and clean judge/demo residue from public docs.

Until items 1-5 are closed, describe Pledgebook as a working pilot rather than
a production-ready financial collection system.
